# 原地改写后的媒体库同步

## 适用范围

`core.rewrite.MediaStoreUpdater`、`core.compress.CompressionEngine` 的原地压缩/恢复。真机参考为 GT7 Pro / Android 16；其他厂商能力需另行验证。

## 已验证的规则

- 原地写文件且恢复 mtime 后，普通扫描可能认为没有变化；直接更新 `_size` 也可能被 MediaProvider 过滤。成功的返回行数不等于实际字段已更新。
- 在本机上，对已发布的同一 URI 显式更新 `IS_PENDING=0` 可触发强制扫描，重新计算 `_size` 和厂商 `o_video_size`。
- 保持 pending=0。不得为此设 pending=1、改名、删除再插入条目，或清空相册数据。
- `o_video_size` 对应 XMP MotionPhoto 的整体段长度，包含主视频和厂商尾部，不能用仅主视频的 `OpCamera:VideoLength` 替代。

## 成功判据

1. 写前后的媒体 URI、ID、路径和发布状态一致。
2. 扫描读回的大小等于实际文件大小；存在厂商列时，实况段长度与文件中的 XMP 解析结果一致。
3. 分别检查 `DATE_TAKEN`、`DATE_ADDED`、`DATE_MODIFIED`。UI 日期回退值不能写成数据库原始 null/0 拍摄日期。
4. 刷新不改变文件内容或文件修改时间；inode/创建时间与完整写入流程的保留要求需分别验收，不能用相册日期替代。
5. 不吞刷新异常。压缩流程应恢复备份并校验内容；区分文件恢复成功、相册同步失败及文件恢复失败，保留恢复失败时的备份。

## 回归与诊断边界

见 `LivePhotoStoreRefreshTest`，只操作新建的独占测试副本。测试分别覆盖本应用来源、其他来源、路径拒绝、完整压缩/还原。外部来源 URI 必须显式传入并检查专用目录/文件前缀，禁止自动挑选用户媒体作为写入对象。

GT7 Pro 的后台清理可结束长时间的 instrumentation 进程；完整编码测试保持目标 APP 在前台。进程中断不算通过，需要读回明确的测试结果后重跑。

最终兼容性须以原厂相册播放验证为准；独立视频解码或 APP 自己播放不能替代原厂验证。个人样本、元数据、恢复备份和原始诊断保存在忽略目录。

## 恢复入口与只读日期（2026-10-16）

RMX5010 当前 Android17/API37 的故障证据：原片与原始备份摘要、拍摄日期和 mtime 完全符合期望，原媒体行已消失，同路径有新行且 DATE_ADDED 不同。普通 ContentResolver 更新不能保证写回旧日期。恢复应先解析现有路径对应行，校验尺寸/实况索引后独立比较原日期；仅日期差异使用部分恢复结果并持久保护。不得把恢复入口接受新行的策略用于普通压缩成功判据，也不得让旧缓存 DATE_MODIFIED 成为恢复后重新扫描的错误目标。

DATE_TAKEN 的 null/0 必须与 UI 的 DATE_ADDED 日期回退区分；还原时不得将界面回退日期写成原始拍摄时间。日期写回的返回行数不能代替读回，各字段差异应具名。

恢复可在摘要/文件身份/路径/owner/未进回收站均验证后结束已有的自身 pending 发布；这与为刷新把已发布行设 pending=1 是不同路径，后者仍禁止。其他来源或 owner 不明的 pending 行仍保护，不擅自发布。用户显式接受当前加入相册时间时，只有 DATE_ADDED 允许采用当前读回值，其他日期和完整性检查仍严格，原始期望保留到完整收尾。
