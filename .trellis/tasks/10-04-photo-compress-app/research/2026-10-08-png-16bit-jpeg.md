# PNG 16 位转 JPEG：放开位深闸门（2026-10-08）

## 原因与边界

用户样例命中「PNG 当前仅支持 8 位静态图片，已保留原片」。判定语句在 `PngCompressor.kt:64`（`probe`，扫描期）与 `:208`（`parse`，压缩期），真正的拦截条件是 IHDR `bitDepth != 8` —— `colorType in {0,2,3,4,6}` 在 PNG 规范下恒成立。命中的是 16 位（色彩类型 0/2/4/6）与 1/2/4 位（0 灰度 / 3 调色板）两类文件。

卡 8 位原本有三条约束：`Image.stride = width * channels` 假设 1 字节/样本；出口链路只有 8 位（`BitmapFactory` ARGB_8888 → `Bitmap.compress(JPEG)`）；规范 `png-jpeg.md` 明定「高位深跳过原片」。

用户在 A/B 两条路线中选定**方案 A：16 位 → 8 位 → JPEG**。变更范围限定为位深闸门、滤波左邻距离、账本 `codecUsed`、设置页说明文案、规范与 README；媒体事务、备份、还原、恢复日志链路未改。

## 实现要点

| 位置 | 改动 |
| --- | --- |
| `PngCompressor.depthReason` | 新增统一闸门，`probe` 与 `parse` 共用：放行 8/16 位；1/2/4 位给「低色深」原因；16 位配调色板判非法；非法色彩类型单独原因 |
| `Image` | 增 `bitDepth`、`sampleBytes`；`stride = width * channels * sampleBytes` |
| `predictor` | 参数 `channels` 改为 `bpp = channels * sampleBytes`，滤波仍在字节层运算 |
| `Encoded` | 增 `bitDepth`，供账本区分来源 |
| `CompressionEngine.commitPngJpeg` | 新增 `bitDepth` 入参，16 位记 `PNG16 → JPEG q=N` |
| `SettingsScreen` | 「压缩PNG」增副标题：符合条件的 PNG 转为 JPEG；16 位会降为 8 位 |

资源上限不分位深：16 位与 8 位共用同一张 ARGB_8888 位图与同一条 32 MiB / 1600 万像素判定，峰值内存一致。

## 验证结果

- 新增 JVM 单测 `app/src/test/.../core/png/PngCompressorTest.kt`，5 项全通过：8 位全色彩类型放行、16 位 0/2/4/6 放行、1/2/4 位给低色深原因且文案不再出现「仅支持 8 位」、16 位配调色板拒绝、非法色彩类型拒绝。
- `./gradlew :app:testDebugUnitTest :app:assembleDebugAndroidTest :app:assembleDebug` BUILD SUCCESSFUL（11 秒，43 任务执行）；单测合计 72 项、0 失败。
- 新增 `app/src/androidTest/.../PngCompressorTest.kt` 覆盖 16 位端到端（0/2/4/6 编码尺寸与唯一标记、非满量程透明度仍按透明跳过、8 位行为不变）。合成样本按 ×257 满量程展开，不依赖私有样张。

## 未验证与边界

- 16 位端到端**未在真机执行**：设备 RMX5010（adb `90d3e7c6`）当前未连接，androidTest 只完成编译打包（`assembleDebugAndroidTest`），未运行。平台编码器把 16 位样本降到 8 位是四舍五入还是截断未实测，因此是否需要在 16 位源上加抖动、以及灰度 16 位解码后的色彩空间是否与 JPEG 输出一致，均待真机结论。
- 未做 16 位渐变样本的肉眼色带验收；未对真实 16 位照片跑压缩率对比。
- 1/2/4 位低色深仍不处理，属本次明确范围外。
