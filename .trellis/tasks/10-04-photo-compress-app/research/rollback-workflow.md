# 失败回滚与回收站职责调整

用户要求：解释清理保护提示，失败照片事务回滚后仍在未压缩页；删除回收站找回照片板块，不把失败处理项展示为回收站内容。

根因证据：commit catch 在普通异常回滚成功后没有清理本次备份，恢复入口却已清除，产生无登记备份；媒体刷新失败时 forgetPublished 未执行，可能残留 DONE。recover 成功也留存原始备份并变成无登记文件。清理将受保护、照片大小变化、照片缺失及真正删除异常都计入 failedCount，统一提示先恢复原片，含义不准确。137 份的真机逐项来源未读取，不能将全部判为同一种故障。

变更范围：

- CompressionEngine：失败回滚始终撤销本次成功登记；完整回滚后清理本次备份；未完成事务自动安全重试并保留保护，已恢复内容的历史假 DONE 按原片摘要证据修正为 FAILED，只有完整时间/身份/副本证据通过才清理。
- Ledger：新增 FAILED 状态常量/登记方法，沿用现有字段，不变数据库结构。
- AppViewModel：扫描前重试持久恢复并失效相关缓存；移除旧备份导出 UI 连接，清理区分保护与删除错误。
- UiModel/Albums/Root/Settings：失败条目在未压缩页，未完成时不可重新压缩，可在详情重试恢复；缺失条目使用原恢复记录的占位媒体。回收站只展示成功压缩备份，删除找回/恢复卡片。
- 原位置、元数据、日期、账本及备份保护契约不放宽；无收益 SKIPPED 继续按用户原决策归类。

未知来源的历史备份只移除产品板块，不批量删除。无法完整回滚不能冒充成功或丢弃唯一备份。本次只在虚拟机生成副本和注入受控失败验收，不修改真机个人媒体。

## API 36 原生验收（0.1.26）

全部为专门生成的合成 JPEG，仅在 emulator-5580 操作，未访问真机个人媒体。

- SQLite 定向 BEFORE INSERT 触发器使实际 APP 压缩的账本提交抛出 `SQLITE_CONSTRAINT_TRIGGER`。APP 报告“原文件及相册记录已恢复”；读回原片与处理前摘要、inode、纳秒 mtime 一致，账本无 DONE、无本次恢复记录，私有目录无该照片的残留备份。失败照片仍在未压缩页。
- 旧假 DONE：源文件仍为原始内容，但账本错误记录压缩后大小与备份。启动后根据摘要修正，当前原片内容与 inode/mtime 未改变，不再作为 DONE 展示。
- 写入中断：故障注入留下三字节文件，有原始备份与持久入口。APP 自动写回完整原片，字节摘要与原图一致。注入方式导致 MediaStore DATE_ADDED 改变，Android 拒绝写回旧日期，因此仍保留恢复入口并显示处理失败，不冒充事务完全通过；未压缩详情可重试，仍明确报告日期未恢复。
- 坏备份：原片备份摘要不符，APP 拒绝覆盖当前可用 JPEG，其摘要保持注入后的值。
- 旧无登记副本的摘要保持；回收站显示为空，无“找回照片”、历史异常备份或失败恢复卡片。恢复重试入口只在未压缩照片详情。

调试及正式 APK 构建成功、签名检查通过。只修改既有安全测试断言以对应新计数和收尾契约，没有新增或运行测试套件。上述验收不代表真机 137 份全部恢复，也不将文件修改时间视为创建时间证明。

SQL 故障项的 MediaStore ID/DATE_ADDED/DATE_MODIFIED/DATE_TAKEN 也与处理前一致；验收完移除了虚拟机定向故障触发器。全量 lintDebug 仍被 VideoTranscoder 358/377 两个既有 WrongConstant 错误阻断，视频文件未改动；发布必需 Lint 与编译通过。新增占位 URI 代码的 KTX 建议已就地修正，不扩展修改旧视频模块。
