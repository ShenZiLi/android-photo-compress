## 修复：页面跳转过渡动画掉帧

**根因**：切页首帧在**主线程**同步跑多轮整库派生计算。

`UiState` 的派生列表（`todoItems()` / `doneItems()` / `albumTodoAll()` / `albumDoneAll()` /
`totals()`）原本每次调用都从头重算，而切一次页会调用 4~6 次：

- `AppRoot`：`todoSelection()` + `doneSelection()`（各触发一次）
- 目标页再触发一次（`TodoLevel1.albumTodoAll()` / `HomeScreen.totals()`）

每次 `todoItems()` 内部含 1 次 `items.associateBy{}`（5199 项建表）+ 3 次全量遍历 + 1 次
5199 个路径建 Set；`doneItems()` 更是套了两层 `associateBy`。切到首页合计约 6 次
`associateBy` + 10 次全量扫描 ≈ **30~50 ms 主线程阻塞** → 120Hz 下丢 4~6 帧。

**改法**（`AppUiModel.kt` / `AppViewModel.kt` / `RecoveryJournal.kt`）：

- 新增 `LibrarySnapshot`：构造时一次性算好全部派生结果，只依赖 媒体库/账本/恢复日志/设置
- `UiState` 增 `library` 字段。它是 data class 构造参数，`copy(page = …)` 时会**原样带过去**，
  所以切页 / 选中变化完全不重算；`LibrarySnapshot` 用引用相等（不覆写 equals），
  与 `UiState.equals` 不会互相递归
- `AppViewModel.rebuildLibrary()`：在 `Dispatchers.Default` 上重建，只在
  扫描结果、`reloadLedger()`、设置变化三处调用；`matches()` 按列表引用 O(1) 命中
- 各处 `UiState.xxx()` 扩展改为委托 `library.xxx`，调用点零改动
- `AlbumTodoUi` / `AlbumDoneUi` 的聚合 `get()` 改为类体 `val`（原先每张卡片每次重组都重算
  一遍该图集的 filter/count）；`DoneMedia.kind` 同理（原先每次访问都走 `MediaKind.valueOf`）
- `RecoveryJournal.Entry.paths` 由 `get()` 改为 `val`（原先 `matches()` 每次调用都重建 list+set）

## 视频压缩固定单线程（不受「加速压缩」开关影响）

`AppViewModel.compress()` 的并发池拆成两个：

- 图片 → `Semaphore(parallelism)`（路数仍由开关 + 可用内存决定）
- 视频 → `Semaphore(1)` 独占池，任何时刻至多一个视频在转码

关键约束：**只有 `parallelism > 1` 时视频才分流到独占池**；否则图片与视频共用同一把
`gate(1)`。若两条池无条件独立，开关关闭（parallelism=1）时图片与视频会各持一把锁并行跑，
破坏「关闭即单线程」语义。

其它改动：

- 任务执行体抽成 `runOne: suspend (MediaItem) -> Unit`，两条池共用同一套结果统计与进度更新
- 当前项名称只在串行路径展示：`parallelism <= 1 || item.kind == VIDEO`
- 批次标签「N 路并发」仅在「并行度 > 1 且非视频项 > 1」时显示

理由：`VideoTranscoder` 每次转码都新建 MediaCodec 硬编码器实例，实例数有限，多路并发
互相抢占会变慢甚至转码失败。

**已确认（2026-10-08）**：live photo 的内嵌视频段虽然同样走 `VideoTranscoder`
（`CompressionEngine.kt:423`，失败降级为「原样保留」，不会损坏文件），但**不纳入串行池**，
保持并发 —— 内嵌视频通常只有 1~3 秒、主体是 JPEG 重编码，串行化会白白牺牲吞吐。
即串行池只覆盖 `MediaKind.VIDEO`。

编译 `assembleDebug` SUCCESSFUL，`testDebugUnitTest` 全通过。真机验证待设备重新连接。

## PNG「仅支持 8 位静态图片」跳过：原因定位与方案评估（仅分析，未动代码）

- 文案来源两处：`PngCompressor.kt:64`（`probe`，扫描期）与 `:208`（`parse`，压缩期）；
  经 `MediaRepository.kt:212-215` 转为 `SupportDecision.Skipped` 显示在原片项上。
- 真正拦截条件是 IHDR `bitDepth != 8`——`colorType in {0,2,3,4,6}` 在 PNG 规范下恒成立
  （非法组合只有 1/5，实际文件不会出现）。命中两类：16 位（颜色类型 0/2/4/6）与
  1/2/4 位（0 灰度 / 3 调色板）。
- 卡 8 位的三条原因：① `Image.stride = width * channels` 假设 1 字节/样本，16 位行宽 2 倍、
  低位深是位打包，滤波重建与 PLTE 索引检查都会读错；② 出口只有 8 位
  （`BitmapFactory` ARGB_8888 → `Bitmap.compress(JPEG)`），16 位必然不可逆降精度；
  ③ spec `png-jpeg.md` 明定「高位深跳过原片」。
- 评估结论：**可压**。A 16→8 位转 JPEG（复用现成 `PngConversionRewriter` 事务，成本最低）；
  B 16→8 位原地重写 PNG（复用 `CompressionEngine.kt:620-690` HEIC 原地事务骨架 + 已有 PNG
  解析器，需补逆向滤波 + `Deflater` 写出）；C 16 位无损重压（成本高、收益不确定）；
  D 低比特深不做。
- 已建议 P0（0 风险）先做文案分层，把 16 位与低比特深分成两条提示；P1 待立立拍板选 A 还是 B。

## 真机部署 + 16 位端到端验证（RMX5010，已连 USB）

设备 `90d3e7c6` 已重新连接，完成装机与真机验证。

**装机命令（复用）**
```

adb -s 90d3e7c6 install -r -t app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
adb -s 90d3e7c6 shell am instrument -w -e class com.photocompress.app.PngCompressorTest \
  com.photocompress.app.test/androidx.test.runner.AndroidJUnitRunner
```

**真机抓到真实 bug（JVM 单测测不出）**：`PngCompressor.compress()` 的保真守卫
`decoded.colorSpace == bitmap.colorSpace` 把 16 位整项拦下。实测两个色彩空间：

| | 值 |
|---|---|
| 源（16 位 PNG 解码为 ARGB_8888） | `scRGB-nl IEC 61966-2-2:2003`（Android `EXTENDED_SRGB`） |
| 输出（JPEG 再解码） | `sRGB IEC61966-2.1` |

二者天然不等，属 16 位→8 位的必然降级，不是缺陷。**修法**：尺寸必须相等；色彩空间
`decoded.colorSpace == bitmap.colorSpace || (image.bitDepth == 16 && decoded.colorSpace?.isSrgb == true)`。
8 位源仍要求完全一致，既有行为不变。注意 `Bitmap.colorSpace` 是可空类型，写 `isSrgb`
必须走 `?.`。

**结果**：`PngCompressorTest` 真机 4 项全过（16 位灰度/RGB/RGBA 端到端 + 透明跳过 +
位深闸门 + 8 位回归）；JVM 单测 72 项 0 失败。

**设置页文案最终定稿**：压缩PNG 副标题 = **「压缩后转为JPEG」**（原「符合条件的 PNG
转为 JPEG；16 位会降为 8 位」）。位深降级披露改由 `codecUsed`（`PNG16 → JPEG q=N`）
与 spec 承担，UI 不展开。已真机目视校验。

## 排查：重装后首页/设置页扫不到相册（环境问题，非代码）

用户反馈「首页未扫描到本机相册、设置页看不到图集」。排查结论如下。

**设备事实**：`content query --uri content://media/external/images/media` 有 **8769 张图片 / 59 个视频**；
app 首页显示「已扫描本机媒体 · 15:16」+ 未压缩 0 项，即扫描**跑完了但结果为空**。

**能力状态（关键）**

| 项 | 值 | 含义 |
|---|---|---|
| `Uid mode: MANAGE_EXTERNAL_STORAGE` | `allow` | 所有文件访问**已允许** |
| 包级 `MANAGE_EXTERNAL_STORAGE` | `default` | 继承 UID 级 → 综合为 allow |
| `READ_MEDIA_IMAGES` / `READ_MEDIA_VIDEO` | `granted=false`，无 `USER_SET` 标志 | 用户从未授权过这两个运行时权限 |
| `READ_EXTERNAL_STORAGE` / `WRITE_EXTERNAL_STORAGE` | `ignore` | 同上 |

`StorageAccess.hasAllFilesAccess()` 走 `Environment.isExternalStorageManager()`（`StorageAccess.kt:15`），
按 `cmd appops` 的 UID 级 allow 判定应为 true —— 间接佐证：全量 instrument 里
`LivePhotoStoreRefreshTest` 的 `check(Environment.isExternalStorageManager())` 是**通过**的。

**因此怀疑点是「扫描结果缓存」**：app 记录的时间戳是 15:16，即重装后第一次扫描；
该次扫描结果为空并被沿用。**未确认**是否需重新扫描即可恢复（手机当时已息屏锁屏，adb 无法继续）。

**本机 adb 排障坑（ColorOS / Android 16，值得复用）**

- **`adb install -r` 重装后需留意存储权限状态**：本次重装后 `READ_MEDIA_*` 与
  `MANAGE_EXTERNAL_STORAGE` 均处于未授予/default 状态。重装前数据正常、重装后为空。
- **shell 无法授予任何权限**：`pm grant` → `Neither user 2000 nor current process has
  GRANT_RUNTIME_PERMISSIONS`；`appops set`（含 `--uid`）→ 无 `MANAGE_APP_OPS_MODES`。
- **`am instrument -g` 不存在** → `Error: Unknown option: -g`。
- **跳「所有文件访问」页可用**（注意 package 参数必须整串加引号，否则被截断为 `package:`）：
  ```
  adb shell "am start -a android.settings.MANAGE_APP_ALL_FILES_ACCESS_PERMISSION -d package:com.photocompress.app"
  ```
- **息屏会让 adb 操作全部静默失效**：此时 `dumpsys window` 的 `mCurrentFocus` 卡在
  `NotificationShade`，`uiautomator dump` 返回空、`input tap` 无效、`am start` 起不到前台；
  截图只有 20 KB 全黑。先 `input keyevent KEYCODE_WAKEUP` 唤醒，若仍为锁屏则需用户手动解锁。
- **`input tap` 避开屏幕顶部 ~300px**：ROP 高 2780px，顶部属状态栏下拉手势区，误触会拉下通知栏。
