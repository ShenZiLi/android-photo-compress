## 10bit HDR 视频压缩：D11 由「首版不处理」改为「保真或跳过」

主体拍板：策略 A（跳过）+ 保留既有未提交改动继续迭代 + 代码与文档一起提交。

### 决策要点

- **核心原则**：HDR 源要么保真压缩，要么跳过；**禁止静默降级为 SDR 落地**。
- 三候选方案：A 跳过（采纳）/ B 降级+提示 / C 用户可选。选 A 的理由是「保留视频原始信息」是硬要求，
  降级即使有提示也构成事实违约，不应把决策成本转给用户。
- 未选 C 是首版不引入交互成本。

### 实现

- 删除 `HdrMode.SDR_CLEAR` 及「保真失败→自动转 SDR」整条降级链。
- 能力门槛 `MediaClassifier.deviceCanPreserveHdr`（`by lazy` 进程级缓存）。
- **判类保持纯逻辑**：`decideVideo` 的 `canPreserveHdr` 做成惰性提供器 `() -> Boolean`，
  仅在源为 HDR 时求值 —— 因为 JVM 单测里 `MediaCodecList` 是桩实现，非 HDR 路径不得触碰它。
  这是本次踩到的坑：默认参数会在调用点直接求值，导致 `getCodecInfos not mocked`。
- 新增 `VideoProbeRunner.scanHevcConfig`（直读 `hvcC` 取 profile/位深），
  `probe()` 在 MediaExtractor 缺省这两项时自动兜底。
- `buildColorPatch` 在「源无任何色彩标注」时按 BT.2020 + PQ 补齐 signaling。

### 样本实测（重要）

`local-test-media/videos/vid_10bit_hdr.mp4` 的真实属性：
- `hvcC` profile_idc = **2**（Main10）、bitDepthLumaMinus8 = **2**（10bit）
- **没有 `colr` box**，也无 HDR 传递特性标注

即「裸 10bit Main10、无 signaling」，正好是兜底链的靶子。
（解析要点：`hvcC` 里 bitDepthLumaMinus8 在偏移 **17**，不是 13；13 是 minSpatialSegmentation。

- **U4c**：保真产物 colr/hvcC 一致 + 相册观感不发灰

## 真机实测暴露的缓存 bug（同日 16:00 修复）

### 现象

主体反馈：相册里 HDR 视频仍显示 **「10-bit HDR 视频本版本不处理」**，要求支持压缩。
但该文案在代码里**早已删除**（D11 已改为「保真或跳过」）。

### 根因（已确证）

真机 `media_cache` 表实测：**52 条**记录带着旧文案，且 `videoCodec` 全部是
**`video/dolby-vision`**（杜比视界）。

`diffCache` 只比对 `dataPath / dateAddedSec / dateModifiedSec` —— 视频文件本身没变，
于是被判为「未变化」直接复用缓存里的旧 `skipReason`。**新判类逻辑根本没机会执行。**

> 教训：**文件没变 ≠ 判类结果没变。** 缓存有效性必须把「判类逻辑版本」算进去。

### 修复（提交 `7445c1a`）

- `MediaCache.kt`：新增 `CACHE_LOGIC_VERSION` 常量 + 纯函数 `needsFullScan()`，
  并写明「改动判类/探测逻辑时必须 +1」。
- `Ledger.kt`：`SettingsEntity` 加 `cacheLogicVersion`；DB **v4 → v5**，`MIGRATION_4_5`
  默认 0 ≠ 当前常量 → 升级后自动全量重扫。
- `AppViewModel`：`warm = !needsFullScan(...)`；扫描成功后回写版本。
- 单测 +4 条（首次启动 / 正常增量 / 版本过期 / 版本超前）。

**真机验证**：`cacheLogicVersion=1`、旧文案 52→0、52 条 DV 记录 `skipReason` 全变 NULL。

### ⚠️ 顺带发现的重要问题：主体那 52 条是杜比视界，不是普通 HDR10

设备确有 `c2.qti.dv.decoder` / `c2.qti.dv.encoder`（**能解码**）。
但 Android 公开 API（MediaMuxer）**无法写回杜比视界的 RPU 增强层**。

我们的 `HdrMode.PRESERVE` 只做 HEVC Main10 + HDR10 静态元数据 →
**保住 10bit 位深 / PQ 传递特性 / BT.2020 宽色域，丢掉 DV 动态元数据**，
产物实质是 HDR10 而非杜比视界。

**已向主体提出待拍板**：A 按 HDR10 保真压缩并标注（推荐）/ B DV 跳过 / C 保留原样。
未拍板前不要在代码里对 DV 做特殊分支。

## 首页对比图例对齐修复（提交 `cba6bf0`）

主体贴截图 + 一句「垂直对齐」，红框圈住两处图例的「已压缩」。

### 定位方法（可复用）

Compose 的节点在 `uiautomator dump` 里被合并，拿不到文本 bounds —— 改用**截图像素分析**
（Pillow 已在隔离 venv `~/.workbuddy/binaries/python/envs/default`，无需另装）。

按色块颜色（`dataTodo` 蓝 / `dataDone` 绿）扫描行区间，再分别求各色块的 x/y 范围：

| 位置 | 「已压缩」色块起点 x | 垂直中心 y |
|---|---|---|
| 顶部统计卡 | 350 | 471.5 |
| 数量对比图例 | **232** | 754.0 |
| 体积对比图例 | **268** | 902.0 |

**结论：y 方向完全对齐（差 ≤1px = 抗锯齿噪声），问题在 x 方向。**
中文语境里的「垂直对齐」= 落在同一条**竖直**线上，即 x 对齐。

### 根因与修复

根因：图例用 `spacedBy(16.dp)` **紧挨排列**，右栏起点随左栏文字长度浮动；
而上方 `StatsRow` 用 `weight(1f)` **两等分栏**。两套布局语言，自然对不上。

修复：让图例与 StatsRow 共用同一条水平网格 ——
同宽（外层去掉水平内边距，图例直接 `fillMaxWidth`）、同间隔（12dp）、同内容内缩（16dp）。
做法是把 `CardSurface` 内层 `padding(16.dp)` 拆成 `padding(vertical = 16.dp)`，
水平内边距下放给 `CompareMetric`（标题行 / 进度条各补 16dp，图例行不分摊）。

> 教训：同一屏内若有两组「同类元素」（这里是顶栏 vs 图例），
> **必须共用同一套网格参数**；否则文字长度一变，右栏位置就漂。

主体指示「无需装机验证」，故本次未做装机复测，仅编译通过 + 提交。

## 视频压缩后相机信息丢失（提交 `af335c6`）

主体报告「视频压缩后丢失了相机信息」。

### 定位方式（值得复用）

写了一个 androidTest `VideoMetadataPreservedTest`：真机上跑完整链路
（`VideoTranscoder.transcode` → `Mp4Metadata.inject`），**逐字节比对**源/产物的 moov 元数据框。

**关键**：一开始只查「框是否存在」，结果**误判通过**——因为 MediaMuxer 自己会写一个
约 118B 的空 `moov/meta`，存在性检查看不出它把源的真 meta 顶掉了。
**改成比较字节内容才暴露问题。**

实测结果（源 `VID20261001190606.mp4`，4.6MB，HEVC）：

| 框 | 修复前 | 修复后 |
|---|---|---|
| `udta`（GPS + OPPO 私有块 614KB） | ✅ 一致 | ✅ 一致 |
| `meta`（相机 QuickTime 键 447B） | ⚠️ **被产物 118B 空框顶替** | ✅ 447B 一致 |
| `titl`（厂商私有 `Oplus_0`） | ❌ **丢失** | ✅ 15B 一致 |

### 两个独立缺陷

1. `inject` 的替换条件里有 `if (!hasSame || b.type == "udta")` —— **产物已有同类型框就跳过**。
   MediaMuxer 自带空 meta，导致源 meta 被丢弃。
2. `extractMetaBoxes` 只挑 `udta` / `meta` —— **白名单漏掉厂商私有框**（realme 的 `titl`）。

### 修复原则

- **排除法代替白名单**：搬 moov 下除 `mvhd`/`trak`/`mvex`/`iods`/`drm`/`pssh` 之外的全部子框。
- **源一律为准**：同名框一律替换，不看产物是否已有。

### 真机验证命令（两段式）

```bash
# 1) 跑测试
adb install -r app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
adb shell am instrument -w -e class <TestClass> \
  com.photocompress.app.test/androidx.test.runner.AndroidJUnitRunner
# 2) 抓自定义 tag 的日志
adb logcat -d -s PCMETAVERIFY
```

### 踩坑

- 我写的测试辅助函数 `moovChildBoxMap` 用 `readBytes()` + Int 索引，**对同一文件返回空 Map**，
  而 `moovChildTypes`（RandomAccessFile + Long 偏移）正常。排查耗了几轮。
  **教训：MP4 解析统一用 RandomAccessFile + Long 偏移，别图省事 readBytes + Int。**

## 首页饼图改为三类媒体占用占比（提交 `c036d4f`）

主体要求：饼图内容改为展示「普通图片 / 实况图片 / 视频」占据内存百分比。

### 口径（关键决策）

**当前实际占用**，不是压缩前体积：
- 未压缩 → `MediaItem.size`（原始大小）
- 已压缩 → `item?.size`（实时文件大小），文件不在库时退回 `record.compressedSize`
- 不含被排除图集（与 StatsRow / 对比条保持同一口径，避免同一屏数字互相矛盾）

实现：`Totals` 加 `kindBytes: Map<MediaKind, Long>`，在 `totals()` 里汇总。

### 实现要点

- `AppColors` 新增 `kindPhoto` / `kindLive` / `kindVideo`（蓝 / 紫 / 橙，明暗各一套）。
  **与 `dataTodo` / `dataDone` 是不同维度**（那是处理状态，这三个是媒体类型），别混用。
- 环形图用 `StrokeCap.Butt` 而非圆头：圆头会让相邻段互相压边，段越短占比失真越明显。
- 某类为 0 时跳过绘制，避免零宽弧毛刺。
- 保留了「已节约 XX / N%」摘要（移到卡片底部），不因换饼图丢信息。

真机在操作中途断开（`no devices found`），**未做装机验证**，仅编译通过。
主体此前也表达过偏好跳过装机验证。

### 项目测试策略（重要）

JVM 单测无法构造 → **现有测试一律把逻辑抽成纯函数再测**（如 `MediaClassifier.imageFormat`）。

## 实况照片压缩后相册无法播放（根因已定位，方案待拍板）

主体报告：实况压缩后 ColorOS 相册播不了。

### 结论：文件没问题，问题在 MediaStore

**文件侧逐项验证全部通过**（压缩 25,064,354 → 8,893,299）：
段边界、XMP 结构（只改两个数字）、MPF、主视频 MP4、尾块索引、APP 段 —— 全部自洽。

**真凶是 MediaStore 的 `o_video_size`。** 用一条**未压缩**的实况照片反推出字段语义：

```
IMG20261005145900.jpg: _size=12,651,333  o_video_size=8,224,204
验算 12,651,333 − 4,427,129(MotionPhoto 起始偏移) = 8,224,204  ✓
```

→ **`o_video_size` = 文件内 MotionPhoto 段的长度**，oplus 相册靠它定位内嵌视频。

压缩后该字段仍是旧值：`o_video_size=17,377,612`，而文件里只剩 **5,864,993** →
相册按 17.4MB 去读 5.9MB 的段 → **越界 → 播不了**。

### 三条路都堵死（别重复试）

| 手段 | 结果 |
|---|---|
| `contentResolver.update`（含 oplus 私有列） | **影响行数 = 0**，被 MediaProvider 拒绝 |
| `scanFile`（mtime 已恢复原值） | 扫描器认为文件没变，**跳过重解析** |
| 人为改新 mtime 后再 `scanFile` | **仍然不更新** |

推测 oplus 的 MediaProvider 只在**插入新行**时算 `o_video_size`。

### ⚠️ 设计层面的根本冲突（重要教训）

**「原地改写 + 恢复 mtime」与 MediaStore 天然打架** ——
恢复 mtime 恰恰是扫描器判定「文件未变」的依据，于是媒体库永远感知不到变更。
**AC4（时间一致）与「让媒体库感知变更」在这里是对立的**，原设计只考虑了前者。

- B 改为「写新文件 + 删旧文件」—— 丢 DATE_ADDED / 相册位置
- C 实况暂不支持压缩 —— 保守回退
