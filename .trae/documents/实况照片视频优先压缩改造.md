# 实况照片「图像保画质 · 重点压视频」改造

## 摘要

当前实况照片压缩几乎只重编码主图（样张占 29.8%），其余 70.2%（增益图 + 内嵌视频 + 厂商私有尾块）逐字节原样复制，因此整体压缩率很低。

本次改造：**主图/增益图维持现有质量档 92/85/76 不变**；把内嵌视频从「整段不可拆」改为**按 `OpCamera:VideoLength` 精确切分**，只重编码内嵌主视频（改用「视频」档位 + 更激进码率系数），**厂商私有尾块逐字节原样保留**，并就地改写 `OpCamera:VideoLength` 与 `Item:Length`(MotionPhoto) 两个数字。

预期收益（以 `C:\Users\Admin\Desktop\实况图片.jpg` 12,478,846 B 为基准）：主视频 5,116,097 B → 约 1.5～2.5 MB，整张照片体积下降约 20%～30%；图像段画质不受影响。

## 现状分析

### 样张实测构成（12,478,846 B）

| 区段 | 位置 | 大小 | 占比 | 当前处理 |
|---|---|---|---|---|
| 主图 JPEG 头部 | [0, 94,839) | 94,839 B | 0.76% | 重建 |
| 主图 4096×3072 像素数据 | [94,839, 3,717,763) | 3,622,924 B | 29.03% | **重编码 q=92/85/76** |
| 增益图 2048×1536 | [3,717,763, 4,147,820) | 430,057 B | 3.45% | 原样保留 |
| **内嵌主视频** 1920×1440 HEVC | [4,147,820, 9,263,917) | **5,116,097 B** | **41.00%** | **原样保留（本次改造点）** |
| **厂商私有尾块** | [9,263,917, 12,478,846) | **3,214,929 B** | **25.76%** | 原样保留（本次不动） |

尾块内部：`src.image` 第二张全尺寸图 2,102,284 B + `live.subVideo` 第二段视频 1,111,772 B + 索引 JSON 546 B。索引条目形如 `{"length":1111772,"name":"live.subVideo","offset":1111772,"version":1}`，**偏移自尾块内容末尾反向计数**，不含对主视频的引用 → 主视频变长变短不影响尾块内部偏移，可整块原样搬移。

### 关键 XMP 事实

- `Item:Semantic="MotionPhoto"` 的 `Item:Length="8331026"` = 主视频 5,116,097 + 尾块 3,214,929（恰好相加，无 Padding）。
- `OpCamera:VideoLength="5116097"` **精确等于内嵌主视频 MP4 的字节长度**（ftyp 24 + moov 2,842 + free 350 + mdat largesize 5,112,881）——**不是时长**。
- 相册靠这两个数字定位内嵌视频，因此两者必须同步改写。

### 根因

`CompressionEngine.kt:257`：

```kotlin
val canReencode = plan.hasMotion && motionBytes != null && LivePhotoContainer.isPlainMp4(motionBytes)
```

`motionBytes` 是整个 8,331,026 B 区段（主视频 + 私有尾块），`isPlainMp4` 要求 box 链恰好耗尽整个数组（`i == bytes.size`），因此对 oplus 复合尾段**恒为 false** → 内嵌视频从不重编码。

## 变更方案

### 1. `VideoTranscoder.kt` —— 新增「激进」码率档位（仅实况内嵌视频启用）

**What**：新增 `BitrateProfile` 枚举与可选参数，`chooseBitrate` 按档位取不同系数。

```kotlin
enum class BitrateProfile { STANDARD, AGGRESSIVE }

fun transcode(input: File, output: File, tier: QualityTier,
              profile: BitrateProfile = BitrateProfile.STANDARD): Result
```

`chooseBitrate`：

```kotlin
val factor = when (profile) {
    BitrateProfile.STANDARD  -> when (tier) { HIGH -> 0.72; BALANCED -> 0.50; COMPACT -> 0.34 }
    BitrateProfile.AGGRESSIVE -> when (tier) { HIGH -> 0.50; BALANCED -> 0.30; COMPACT -> 0.18 }
}
var target = (base * factor).toInt()
if (profile == BitrateProfile.AGGRESSIVE) {
    // 地板：避免极低码率源被压到不可看（约等于「质量参考码率」的 20%）
    val floor = (estimateBitrate(video.width, video.height, video.frameRate) * 0.20).toInt()
    if (target < floor) target = floor
}
encoderBitrateRange(targetMime)?.let { target = target.coerceIn(it.first, it.second) }
```

**Why**：用户裁决「重点压缩视频段允许有一定损失」，且明确范围**仅实况内嵌视频**——`compressVideo` 保持默认 `STANDARD` 调用，普通视频页行为完全不变。地板只作用于 AGGRESSIVE，避免给普通视频引入回归。

### 2. `LivePhotoDetector.kt` —— 暴露 `OpCamera:VideoLength` 读取

**What**：
- `private fun extractVideoLengthUs(text)` → `fun extractVideoLength(xmpText: String): Long`（公开），返回字节长度，去掉误导性的 `Us` 后缀。
- `LiveInfo.videoDurationUs` → `videoLengthBytes`（字段语义修正）。
- 更新内部 2 处调用点（`detectFromHeader` 的两个 return）。

**Why**：引擎需要该值做切分；已 grep 确认 `videoDurationUs` 只在 `MediaRepository.kt:200` 附近被填充、**无 UI/账本消费点**，改名无副作用。

### 3. `LivePhotoContainer.kt` —— 新增切分与改写纯函数

**What**：新增两个方法（不改动现有方法）。

```kotlin
/** 从 motion 区段切出主视频（前缀）与厂商私有尾块（后缀）。
 *  主视频必须自身是合法完整 MP4；否则返回 null（退回整段原样保留）。 */
fun splitMotion(motionBytes: ByteArray, videoLength: Long): Pair<ByteArray, ByteArray>? {
    if (videoLength <= 0 || videoLength >= motionBytes.size) return null
    val video = motionBytes.copyOfRange(0, videoLength.toInt())
    if (!isPlainMp4(video)) return null
    return video to motionBytes.copyOfRange(videoLength.toInt(), motionBytes.size)
}

/** 就地改写 OpCamera:VideoLength 的数字（内嵌视频字节长度），不动 XMP 结构。 */
fun rewriteVideoLength(xmp: String, length: Long): String =
    Regex("""OpCamera:VideoLength="\d*"""").replace(xmp) { "OpCamera:VideoLength=\"$length\"" }
```

**Why**：`rewriteVideoLength` 用 lambda 形式替换，规避替换串中 `$` 转义问题；属性不存在时自然无操作（引擎只在 `extractVideoLength > 0` 时才走新路径）。切分与校验集中在此，便于单测。

### 4. `CompressionEngine.kt` —— 实况照片按视频档位重编码内嵌主视频

**What**：

1. 签名扩展：`compress(item, tier, videoTier)`；`compressPhoto(item, tier, videoTier)` 透传；`compressLivePhoto(item, tier, videoTier)`。
2. `compressLivePhoto` 中新增切分逻辑（仅当 `plan.motionPadding == 0L`，样张即为此情形）：

```kotlin
val videoLength = LivePhotoDetector.extractVideoLength(xmp)
val split = if (plan.hasMotion && motionBytes != null && plan.motionPadding == 0L)
    LivePhotoContainer.splitMotion(motionBytes, videoLength) else null

var newMotionBytes: ByteArray? = null
var newVideoLength = 0L
if (split != null) {
    val (videoPart, tailPart) = split
    val src = File(cacheDir, "pc_motion_src_$ts.mp4").apply { writeBytes(videoPart) }
    val dst = File(cacheDir, "pc_motion_dst_$ts.mp4")
    val res = VideoTranscoder.transcode(src, dst, videoTier, BitrateProfile.AGGRESSIVE)
    if (res.success && dst.exists() && dst.length() < videoPart.size) {
        Mp4Metadata.inject(dst, src)
        val probe = VideoProbeRunner.probe(dst.absolutePath)
        if (probe.codec != null && probe.durationMs > 0) {
            val videoBytes = dst.readBytes()
            newVideoLength = videoBytes.size.toLong()
            // 尾块逐字节原样追加，保证其内部「自末尾反向计数」的索引偏移仍然有效
            newMotionBytes = videoBytes + tailPart
        } else { …回退… }
    } else { …回退… }
    src.delete(); dst.delete()
}
```

3. 组装与 XMP：`motionLen = newMotionBytes?.size ?: motionBytes?.size`，写入时优先写 `newMotionBytes`；XMP 改写顺序为

```kotlin
if (newMotionBytes != null) changed["MotionPhoto"] = motionLen.toLong()
var xmpOut = if (changed.isEmpty()) xmp else LivePhotoContainer.rewriteItemLengths(xmp, changed)
if (newMotionBytes != null) xmpOut = LivePhotoContainer.rewriteVideoLength(xmpOut, newVideoLength)

```

4. 新增分段自校验（仅新路径），在 `magic == "ftyp"` 校验后追加：

```kotlin
val checkText = String(assembled, 0, minOf(256 * 1024, assembled.size), Charsets.ISO_8859_1)
if (LivePhotoDetector.extractVideoLength(checkText) != newVideoLength) return Skipped("实况分段自校验失败(视频长度)")
if (LivePhotoDetector.parseContainerItems(checkText).firstOrNull { it.semantic == "MotionPhoto" }?.length != motionLen.toLong())
    return Skipped("实况分段自校验失败(区段长度)")
```

5. 回退策略（保持既有容错风格）：
   - `split == null`（无 `OpCamera:VideoLength` / 非零 Padding / 主视频非合法 MP4）→ 沿用现有整段 `isPlainMp4` 判定，若为整段普通 MP4 则用 `videoTier + AGGRESSIVE` 整段重编码，否则原样保留。
   - 转码失败、体积未减小、probe 校验不过 → 整段原样保留，`motionNote` 说明原因（不 `Failed`，不影响主图收益）。
6. `motionNote` 文案随路径更新：`"内嵌视频重编码（${res.codec}）"` / `"内嵌视频原样保留（厂商私有封装）"` / `"内嵌视频原样保留（重编码未获益：…）"`。
7. `codecUsed` 保持现有拼接格式：`"JPEG q=$quality + 增益图原样 + $motionNote"`。

**Why**：这是本次收益来源；主图/GainMap 逻辑一行不改，保证画质不回归。

## 假设与决策

| 项 | 决策 | 依据 |
|---|---|---|
| 主图/增益图质量 | 维持 92/85/76，增益图原样保留 | 用户裁决 + 需求「图片段尽量不损失画质」 |
| 内嵌视频档位 | 读 `settings.videoTier`，与 `liveTier` 解耦 | 用户裁决 |
| 激进系数 | 0.50 / 0.30 / 0.18（+ 地板），**仅实况内嵌视频** | 用户裁决「仅实况内嵌视频」；普通视频保持 0.72/0.50/0.34 |
| 厂商私有尾块 | 逐字节原样保留，不改内部 | 用户裁决「本次不动」；其索引偏移自末尾反向计数，搬移安全 |
| `motionPadding != 0` 的机型 | 不走新拆分路径，沿用现有整段逻辑 | 非零 Padding 的搬移/记账未经验证，避免引入未测分支 |
| `OpCamera:VideoLength` 语义 | 字节长度（非时长），字段改名 `videoLengthBytes` | 样张实测 5,116,097 = 主视频 MP4 总长；无消费点，改名安全 |
| 真机相册识别 | **必须真机复验** | 改写 `OpCamera:VideoLength` 后 ColorOS 相册能否播放未验证 |

## 风险与备用方案

- **主要风险**：改写 `OpCamera:VideoLength` / `Item:Length` 后 oplus 相册拒绝播放。缓解：`rewriteVideoLength` 只替换数字、不动 XMP 结构与字节序；保留整段回退路径；真机复验。
- **备用方案**（仅在真机复验失败时启用）：将自有 XMP 标记改写位置从 APP1 XMP 迁至 JPEG 的 `COM` 段，减少对 XMP 段的扰动。
